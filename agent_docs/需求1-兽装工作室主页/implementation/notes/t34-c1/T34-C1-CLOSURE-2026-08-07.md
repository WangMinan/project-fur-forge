## 2. 数据库迁移、约束与兼容边界

新增两个前向迁移，**未修改** 0000–0019。

### 0020_t34_f5_operation_lease

为 `publication_operations` 与 `watermark_operations` 各增加六列：
`attempt`、`lease_owner`、`lease_expires_at`、`heartbeat_at`、
`recovery_reason`、`next_retry_at`，并各建一个 `(status, lease_expires_at)`
索引。

刻意使用 `ALTER TABLE ADD COLUMN` 而不是 SQLite 的 12 步表重建：新增列不会
重新校验既有 CHECK，也不会丢掉迁移 0016 建立的
`publication_operations_failure_insert` / `_update` 触发器与实体索引。迁移后
已验证两个触发器仍在。

约束边界：`attempt >= 0`；`lease_owner` 为 NULL 或 1–200 字符非空白；
`recovery_reason` 只允许 `LEASE_EXPIRED | STARTUP_SCAN | ALREADY_COMMITTED |
NOT_RESUMABLE`。

`attempt` 语义：行创建时为 0，runner 每次在事务内抢到 lease 时 +1。因此首次
执行是 `attempt=1`，进程被杀后接管是 `attempt=2`。

### 0021_t34_f1_site_display_reconcile

新增 `site_display_reconcile_operations`，列结构与 lease 基础设施一致。

选择独立表而不是扩展 `publication_operations`：后者的 `entity_type` /
`operation_type` CHECK 需要 12 步表重建才能加值，而重建会牵动 0016 的触发器。
独立表列名与 lease 列保持一致，因此 `repository/operation-lease.ts` 可以直接
复用同一组语句。

表上有唯一部分索引 `site_display_reconcile_single_active`：同一 scope 同时
只允许一条未完成记录，避免两次运维命令并行生成同一批对象。

### 兼容边界

- 既有数据库只做加列，历史行 `attempt` 默认 0、lease 列为 NULL，因此启动恢复
  把它们视为「无 lease」候选，语义正确；
- 迁移条数断言不再硬编码：`tests/integration/database.test.ts` 与
  `auth-core.test.ts` 从 `meta/_journal.json` 推导数量。每加一个迁移就要改四处
  数字本身没有验证价值，还会掩盖真正的回归。

## 4. operation lease、heartbeat、启动恢复与进程中断证据

### 基础设施

`repository/operation-lease.ts`：

- 抢占在单条 `UPDATE ... WHERE` 内完成，条件为「非终态 且（lease 为空 或
  lease 属于本进程 或 lease 已过期）」，因此两个 runner 不可能同时持有同一
  lease；
- `lease_owner` 是 `主机名/pid/随机后缀` 的进程实例标识，**不含任何 Secret**；
  测试断言它不匹配 `/secret|token|key/i`；
- TTL 60 秒，心跳间隔取 TTL 的三分之一，一次漏更新不会立刻掉 lease；
- `heartbeatOperationLease` 返回 false 即表示 lease 已被接管，调用方必须停止
  提交；
- 提交语句同时对 `status`、业务版本、`attempt` 和 `lease_owner` 做 CAS，不是
  只按 operation id 更新。

`runner/operation-recovery.ts`：扫描非终止且 lease 缺失或过期的 operation，
交给各模块注册的 resumer；不能安全续做的转为 `FAILED` + `recovery_reason`，
因此运行态任务不会永久阻塞新操作。并发上限 2，日志只写 id/attempt/表名。

启动挂载在 `server/plugins/02.operation-recovery.ts`，序号保证它在
`00.runtime-config` 与 `01.database-config` 之后运行。

### 覆盖范围

HOME/PUBLISH、HOME/UPSCALE、WORK/PUBLISH、WORK/UNPUBLISH、
WATERMARK preview/rebuild(apply)、site-display reconcile —— 六类 operation
全部接入。

### 真实进程中断证据

`tests/integration/operation-interrupt.test.ts` **spawn 真实 Node 子进程**，
在三个边界发送 `SIGKILL`，然后用**新的子进程**执行启动恢复：

| 边界 | failpoint 位置 |
| --- | --- |
| 生成阶段 | 第一次 `processPrivateToPublic` 前挂住 |
| 公开对象验证阶段 | 最后一个变体的 `getPublicAnonymous` 前挂住 |
| 数据库提交边界 | 全部对象已生成落库、进入最终提交事务前挂住 |

failpoint 全部位于 `tests/fixtures/operation-interrupt-child.ts`，**生产代码里
没有任何 barrier 或 kill 钩子**。

断言：operation 不永久停在运行态；接管发生在新 attempt 且记录
`recovery_reason=LEASE_EXPIRED`；恢复后 12 个变体齐全（不出现半套
SourceSet）；重复重启幂等（第二、三次扫描 `scanned:0`，对象集合不变）；
lease 未过期时不被抢占，过期后立即可接管；既有有效公开对象不被删除；恢复
日志不含 Object Key、签名 URL 或凭据。

**不是**在同一进程里调用 runner 两次。

### 提交边界的取舍

Hero 发布与作品发布的「业务状态切换」和「operation 置 DONE」在**同一事务**内，
因此不存在「业务已提交但 operation 仍非终态」的窗口：进程被杀只会回滚到提交
前，恢复路径就是在新 attempt 下重跑同一序列。我一开始为这种窗口写了收尾分支，
被既有用例证明是不可达的死代码，已删除。下架路径不同——它先提交状态再逐个删
对象，因此保留了「从残余 cleanup 清单继续」的恢复分支。

### 中断测试发现的真实缺陷

提交边界的 kill 暴露出 `recipe/site-display-recipe.ts` 的复用判定问题：
`generateOne` 在 try 之外校验既有 READY 行，若该行对应的公开对象已消失，探测
抛出 `NoSuchKey` 会让整条 operation 失败，而不是重新生成。已修正为「探测失败
即视为不可复用」。这是本轮唯一由测试发现的生产缺陷。

## 8. readiness 严格迁移校验

`service/readiness.ts` 原本只比较「已应用迁移数量 == 迁移文件数量」，因此
条数相同但历史不同的数据库会错误地报告 ready。现在复用
`migrationState`（与 `assertDatabaseMigrated` 同一实现），同时比较数量、顺序、
`created_at`/`folderMillis` 与 hash。

旧的固定返回 ok 的 `/api/health` 已改为诚实行为：与 `/api/health/ready` 共用同一
判定，未就绪返回 503。`/api/health/live` 与 `/api/health/ready` 仍是正式接口，
Nginx 继续对公网屏蔽三者。

`tests/integration/readiness.test.ts` 七条负/正路径：数量相同但 hash 不同 →
unready；数量相同但顺序不同 → unready；有待应用迁移 → unready；缺基础单例记录
→ unready；数据库文件不存在 → unready；正确数据库 → ready；响应体不含数据库
路径、`studio.db`、SQL、表名、Object Key 或异常栈，且 `checks` 只有布尔值。

构造负路径时发现 drizzle 的 `__drizzle_migrations.id` 列是 `SERIAL`，在 SQLite
里恒为 NULL，因此按 `id` 定位改不到行；测试改用 `rowid` 并断言
`changes === 1`，确保篡改真的发生。

### 完整 E2E 发现并修复的三个缺陷

跑完整 E2E 之前，单元与集成都是绿的，但完整套件抓出三个真实问题：

1. **`/api/health` 变诚实后 E2E 起不来。** Playwright `webServer` 用
   `/api/health` 判断服务就绪，而夹具库在 `globalSetup` 里迁移——它在
   `webServer` **之后**运行。端点正确地返回 503 五分钟，整轮超时。探针改用
   `/api/health/live`（liveness 本来就是为此存在，不碰数据库），readiness 的诚实
   行为保留，并补集成用例钉住两者区别。
2. **失败的水印 operation 无法重试。** `claimOperationLease` 按设计拒绝终态记录，
   但 `retryWatermarkOperation` 在行仍是 `FAILED` 时就调用
   `runPreview`/`runRebuild`，runner 静默什么都不做。这是 F5 引入的真实回归：
   任何 FAILED 的水印预览或应用都变成永久失败。已在重试前先把 FAILED 重新打开，
   与 `retryHeroSlidePublication` 的既有做法一致，并补集成用例（已验证去掉修复
   后该用例失败）。
3. **新的分区并发用例污染了另一条用例。** 它写入 privacy 分区，而
   `public-information.spec.ts` 断言迁移 0015 种入的隐私政策正文，E2E 串行共用
   同一个库。改为写 about 分区。
