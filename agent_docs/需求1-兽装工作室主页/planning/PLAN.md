# 实施计划

> **角色**：描述当前阶段仍有效的技术方案、执行顺序与边界。
> **最后更新**：2026-08-07。
> **当前阶段**：阶段 D · P1 一期增强范围确认；首要候选为返图墙 T35–T36。

## 1. 稳定技术基线

阶段 C 已完成并经用户浏览器人工验收。以下技术基线继续使用，不在阶段 D 推倒重写：

- Nuxt 4、Vue 3、Nitro、Node.js 24、pnpm 11；
- SQLite + Drizzle，单实例、单写者；
- 阿里云 OSS 私有原图 Bucket + 公开衍生图 Bucket；
- 公开 Host 与管理 Host 由同一应用按 Host 严格隔离；
- 永久原图和授权记录私有，公开页只消费预生成且验证完成的衍生图；
- `server/utils/{repository,service,runner,recipe,route}/` 五层边界；
- 持久 operation、attempt、lease、heartbeat、失败清理与启动恢复；
- 资源版本和 409 冲突，不静默覆盖；
- Docker 镜像由 GitHub Actions 构建，正式域名、TLS、线上 Compose、升级与回滚演练留到 T52。

媒体规则继续以
[`../requirements/MEDIA-PUBLICATION-POLICY.md`](../requirements/MEDIA-PUBLICATION-POLICY.md)
为唯一事实源。阶段 D 新增返图用途时必须在该策略中显式登记，不得沿用模糊的“图片”角色。

## 2. 阶段 C 交付基线

阶段 D 可以直接复用以下能力：

- 角色化私有直传、服务端完成核验和过期会话清扫；
- `assets`、`asset_variants`、公开 SourceSet 和不可变 Object Key；
- 活动 `brand-centered-v2` 水印 profile；
- 无水印站点展示与有水印作品保护的明确分离；
- 作品、Hero、水印与 reconcile 的持久 operation 和恢复框架；
- 管理端媒体分区、预览、上传恢复、状态和错误反馈；
- 公开聚合投影、SSR、三视口与无障碍基线；
- 审计日志、Origin、CSRF、Host、可信代理、限流与日志脱敏；
- 迁移、备份、readiness 和严格 migration hash 校验。

返图墙应作为现有媒体与发布体系的一种受控扩展，而不是另起一套上传、公开 URL 或水印逻辑。

## 3. 阶段 D 推荐范围

### 3.1 已确认的核心：T35–T36

阶段 D 的首轮只围绕返图墙形成一个完整垂直切片：

1. 管理员为已有作品录入返图；
2. 原图进入私有 Bucket；
3. 服务端校验媒体并生成轻量水印公开衍生图；
4. 管理员维护公开标题、说明、排序和展示状态；
5. 公开站以图片墙形式浏览返图；
6. 下架、失败、重试和重启后保持可恢复；
7. 可选授权记录只在后台保存，不进入公开 DTO。

### 3.2 尚未授权的扩展

以下任务不与返图墙形成硬依赖，当前只保留为决策项：

- T37：展会掉落、当前展会和完整状态矩阵；
- T38：受限站点文字内容扩展；
- T39：Slug 显式改址历史；
- T40：30 天回收站；
- T41：手机轻量维护闭环。

在用户明确保留前，不为这些任务预建通用表、通用 CMS、通用软删除框架或通用重定向引擎。

## 4. T35 · 返图模型与可选授权记录

### 4.1 领域边界

推荐以独立 `returns`（或语义等价名称）实体表示一次公开返图记录，而不是把返图直接塞进 `work_assets` 的出厂照列表。每条返图至少包含：

- 稳定 UUID；
- 必填 `work_id`，只关联现有作品；
- 公开标题或短说明；
- 可选公开来源显示名；
- 排序位置；
- `draft | published | unpublished`；
- 资源版本和时间戳。

返图图片关系使用独立角色，例如 `return_photo`，保存：

- 资产 ID；
- 位置；
- alt；
- 焦点或展示裁剪；
- 公开衍生状态。

首轮建议一条返图记录支持 1–6 张图片，具体上限在 T35 实施前写入 SPEC。不要把返图混入作品出厂照，也不要让返图改变作品发布状态。

### 4.2 可选授权记录

授权记录只用于后台留痕，不作为强制法律工作流。推荐字段：

- 授权来源或确认渠道，可空；
- 确认时间，可空；
- 内部备注，可空；
- 记录人和版本信息。

这些字段不得进入公开 DTO、日志或导出 artifact。没有填写授权记录时，系统可以提示但不自动阻止保存；是否阻止发布必须由用户另行明确，不由实现者擅自升级为硬门禁。

### 4.3 并发与删除

- 所有更新携带返图资源版本；
- 409 后保留本地草稿并展示最新服务端值；
- 已发布返图的事实字段和媒体关系建议先下架再改；
- 在 T40 未确认前，删除语义保持明确且保守，不提前建设全站回收站；
- 若首轮需要防误删，可以只为返图提供“下架”而暂不提供永久删除。

## 5. T36 · 上传、轻量水印、管理与公开墙

### 5.1 上传与私有资产

返图继续使用条件 PUT 直传私有 OSS：

- 创建上传会话时声明 `return_photo` 角色和返图归属；
- 服务端重新验证摘要、MIME、尺寸、字节数和归属版本；
- 私有 Object Key、签名 URL 和授权备注不得进入公开响应；
- 过期会话沿用现有清扫能力；
- 失败重试创建新会话和新 Key，不覆盖旧对象。

### 5.2 轻量水印

“轻量水印”应与作品保护水印明确区分身份，但优先复用同一活动 Logo 与生成基础设施。实施前需要锁定：

- 返图是否仍居中，还是采用更小的固定安全位置；
- 不透明度与缩放范围；
- 配方版本，例如 `return-wall-v1`；
- 公开宽度、格式和质量集合；
- 是否允许管理员关闭水印。

在未获得新业务决策前，默认建议：返图公开图必须带水印，使用比作品图更轻的固定配置；管理员不能逐图任意关闭，以免公开行为不可预测。

### 5.3 发布与恢复

返图发布应沿用原子发布模式：

1. 固化请求版本；
2. 生成缺失公开变体；
3. 验证公开对象；
4. 原子切换返图状态与公开投影；
5. 写入审计记录；
6. 失败只清理当前 attempt 新建对象，保留旧公开版本。

长任务必须使用持久 operation、attempt、lease、heartbeat 和恢复原因；刷新或 Node 重启后仍可收敛到唯一终态。

### 5.4 管理端

新增独立“返图”入口，不把返图塞进作品编辑器的出厂照分区。管理端至少提供：

- 返图列表、作品筛选和发布状态；
- 创建、编辑、排序、预览、发布和下架；
- 明确的返图图片分区与上传状态；
- 可选授权记录区域，并标注“仅后台可见”；
- 发布检查、持续进度、失败原因和恢复入口；
- 409 草稿保留与重载选择。

作品编辑页可以展示关联返图摘要和跳转入口，但不复制完整编辑器。

### 5.5 公开返图墙

公开路由建议为 `/returns`，并可在作品详情中展示该作品的少量返图入口。最终路由在 T35 前写入 SPEC。

公开墙至少满足：

- 只读取已发布返图和 READY 公开变体；
- 图片优先，文字保持简短；
- 可按作品查看或进入作品详情；
- 不公开授权记录、私有联系人和原图；
- 图片声明固有宽高，避免明显 CLS；
- 手机、平板、桌面无横向溢出，支持键盘与减少动效；
- 单条返图接口失败不应让全站导航或其他页面 500。

首轮不建设公开投稿、点赞、评论、访客账户或社交动态流。

## 6. 推荐实施顺序

### 第一段：T35 后端模型与契约

1. 固化返图范围、媒体数量、水印默认和公开路由；
2. 新增前向迁移、Drizzle schema、约束和索引；
3. 增加共享 Schema、管理 DTO、公开 DTO 和稳定错误 reason；
4. 实现 repository、service、route；
5. 覆盖隐私、版本冲突、非法作品关联和发布状态测试；
6. 独立后端 Review 后再进入 T36。

### 第二段：T36 媒体与发布后端

1. 接入 `return_photo` 上传会话与完成核验；
2. 实现返图轻量水印 recipe/identity；
3. 实现 publication runner、operation 恢复与精确清理；
4. 生成公开投影和 SSR 查询；
5. 覆盖失败、重试、SIGKILL、重复重启和旧公开版本保留；
6. 真实双 Bucket 验证私有原图不可匿名读取、公开衍生图可读。

### 第三段：T36 管理端与公开端

1. 管理端返图列表与编辑页；
2. 上传、排序、alt、授权记录、预览、发布和下架；
3. 公开返图墙与作品关联入口；
4. 390×844、768×1024、1440×900 浏览器检查；
5. console、network、图片解码、焦点、键盘、减少动效和横向溢出检查；
6. 新上下文独立 Review 与用户验收。

### 第四段：决定剩余 D 范围

T35–T36 形成稳定垂直切片后，再决定 T37–T41。被用户取消的任务从 T42 依赖中移除，不通过实现无价值功能来满足编号连续性。

## 7. GitHub Actions 与发布边界

阶段迁移时，最新已核对运行表现为：

- `image-build` 成功；
- `checks` 在 Production build 失败；
- `e2e` 跳过。

该故障已移到 T49，不阻断阶段 D。阶段 D 日常开发仍应运行与变更相关的本地 lint、typecheck、unit、integration、build 和 E2E；但不得把本地结果写成“远端流水线全绿”。

T49 必须在正式发布前：

- 复现并修复最新 `main` 的 Production build 失败；
- 让 Compose 静态检查和后续步骤实际执行；
- 恢复 E2E；
- 取得 `checks`、`image-build`、`e2e` 同一 SHA 全绿。

不得通过删除测试、放宽类型、安全、媒体或 E2E 断言来换取绿色状态。

## 8. 迁移、备份与 readiness

- 不修改已经执行的历史迁移；
- 所有返图模型使用新的前向迁移；
- 同步更新 Drizzle schema、迁移元数据、约束、索引和测试 fixture；
- 迁移前创建验证备份，在副本执行 integrity、foreign key 和 migration hash 校验；
- readiness 继续比较迁移数量、顺序、folderMillis 与 hash；
- readiness 不高频轮询 OSS，真实 Bucket 权限放在 preflight 和门禁测试。

## 9. 非目标

阶段 D 首轮不实现：

- 万能 CMS、任意 HTML、页面搭建器；
- 公开投稿、注册、点赞、评论或社交关系；
- 订单、支付、自动报价和排期；
- 多管理员、RBAC、多实例或分布式队列；
- 为尚未确认的 T37–T40 预建抽象框架；
- 正式域名、TLS、远程自动部署和 Docker Hub 正式发布；
- 为绕过当前 GitHub Actions 故障而降低门禁。
