## 4. T35–T36 推荐执行顺序

### 第一步：锁定返图业务事实

实施前从当前 SPEC、PLAN 和 TASKS 形成一份短范围说明，至少明确：

- 一条返图记录允许多少张图片；
- 是否必须关联已有作品；
- 公开路由和作品详情入口；
- 轻量水印的位置、不透明度、缩放和是否可关闭；
- 可选授权记录字段是否只提示、不阻断发布；
- 删除暂用下架、永久删除，还是返图专用软删除。

只有会改变公开行为或数据事实的问题才交给用户；普通技术取舍由实现者按现有架构完成。

### 第二步：T35 后端

`BACKEND_PRIMARY` 串行完成：

1. 新前向迁移和 Drizzle schema；
2. 返图实体、图片关系、版本、状态和可选授权记录；
3. 管理/公开共享契约与稳定错误 reason；
4. repository、service、route；
5. 隐私、非法关联、版本冲突和状态测试；
6. 实施 note 和当前活文档同步。

完成后由新上下文 `REVIEW` 检查模型边界、迁移、公开 DTO 和隐私，给出可进入 T36 的结论。

### 第三步：T36 媒体与发布后端

`BACKEND_PRIMARY` 完成：

1. `return_photo` 角色化私有直传和完成核验；
2. 返图轻量水印 recipe/identity 与公开 SourceSet；
3. publication operation、失败清理、重试和启动恢复；
4. 公开返图墙查询与作品关联投影；
5. 真实双 Bucket、进程中断和幂等证据；
6. unit、integration、build 和必要 E2E。

不得新建第二套上传器、第二套公开 URL 生成规则或绕过活动品牌资产。

### 第四步：T36 前端

`FRONTEND_PRIMARY` 在后端契约稳定后完成：

1. 独立返图列表和编辑页；
2. 作品筛选、图片上传、排序、alt、公开文案和授权记录；
3. 发布、下架、持续进度、失败和恢复；
4. 409 草稿保留和重载；
5. 公开返图墙与作品详情入口；
6. 三视口、键盘、焦点、图片解码、减少动效和无横向溢出。

前端不得自行猜测字段、版本或公开媒体身份；契约缺失时回到后端补齐。

### 第五步：独立 Review 与用户验收

`REVIEW` 至少检查：

- 私有原图与授权记录不进入公开 DTO、日志或页面；
- 公开返图只使用 READY 轻量水印变体；
- 发布失败和重启不破坏旧公开版本；
- 管理与公开 Host 隔离；
- 页面真实点击、图片内容和布局，而不只看用例数量；
- 三个固定视口与 console/network；
- 当前活文档与代码一致。

Review 通过后由用户执行人工浏览器验收，才能勾选 T35、T36 的用户门禁部分。

## 5. GitHub Actions 处理边界

当前 `quality` 的已知状态是：

- `image-build` 成功；
- `checks` 在 Production build 失败；
- `e2e` 被跳过。

该故障属于阶段 E 的 T49，不阻断 T35–T36。阶段 D 实现者应运行与本次改动相关的本地门禁，并记录真实结果，但：

- 不得把本地通过写成远端全绿；
- 不得在阶段 D 长程任务中顺手扩大范围修复整个流水线，除非用户明确授权；
- 不得删除测试、放宽类型或安全边界来掩盖失败；
- 不得把不同 SHA 的成功结果拼接成一次通过；
- 不得把 `e2e skipped` 记为成功。

T49 会在上线前以最新 `main` 统一复现、修复和验证。
