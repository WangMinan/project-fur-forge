## 2. 实施前现状检查（历史基线）

本节记录 2026-08-11 建立本需求时的只读基线，用于解释后续增量从何而来；不表示当前分支仍缺少这些能力。当前实施事实以 [`../STATE.md`](../STATE.md) 和 [`../implementation/TASKS.md`](../implementation/TASKS.md) 为准。

### 2.1 已有能力

- 导航项已经支持 `children`；桌面端以 hover/focus 显示下拉，面板使用 `var(--radius-lg)`。
- 移动导航已经能展开呈现子项，不需要第二套导航数据。
- 当前分支已把“自设委托”和“角色领养”两个一级项合并为“委托”，子项为“自设委托”与“掉落领养”，路由仍为 `/commission` 与 `/adoptions`。
- `/admin/site/content` 已有独立的 contact 和 commission-faq 分区、版本号、局部保存与 409 草稿保留。
- 后台作品列表按“设定名称 + 物种”做 trim、中文 locale 小写和包含匹配。
- 后台返图列表在 SQLite 中按“设定名称 + 昵称”做包含匹配。
- 三个公开列表已有 SSR、普通链接分页与受控空态。

### 2.2 缺失能力

- 联系区只有邮箱、QQ、抖音文本，没有五个平台的统一结构、Logo 或二维码。
- 委托 FAQ 没有可直接套用的邮件估价模板。
- 三个公开列表 API 都不接受设定名称查询。
- 没有“最新动态”的公开路由、首页摘要、管理能力或持久模型。

## 3. 目标

1. 减少一级导航冗余，同时保持委托和领养入口可发现、可键盘操作。
2. 让访客能直观看到五个平台的官方身份、二维码和账号，降低找错账号的风险。
3. 给委托人一份可复制填写的邮件估价资料清单，但不提前建设邮件发送功能。
4. 让访客能按设定名称定位作品、返图和领养内容，并保持筛选、随机顺序与分页正确。
5. 给工作室一个发布参展资讯、掉落预告、开单通知和其它公告的统一入口，并在首页露出最新内容。

## 4. 功能契约

### FR-01 · 合并委托导航

- 桌面一级导航把“自设委托”和“角色领养”合并为“委托”。
- “委托”下拉包含：
  - “自设委托” → `/commission`；
  - “掉落领养” → `/adoptions`。
- `/commission` 与 `/adoptions` 路由、页面标题和既有兼容链接不改变。
- “掉落领养”只替换导航中的旧“角色领养”标签；`/adoptions` 仍包含常规领养与展会掉落，不因该名称变化增加过滤或改变数据模型。
- “委托”下拉必须复用“关于我们”的同一结构、阴影、间距与 `var(--radius-lg)`，不得复制第二套样式。
- hover、键盘 focus-within 均可打开；子项可 Tab 到达；当前位于任一子路由时父项显示激活。
- 移动端继续由同一 `PUBLIC_NAV_ITEMS` 数据生成两个子入口，不依赖 hover。

### FR-02 · 五个平台联系方式卡片

- 现有邮箱按钮与邮箱地址保留在联系区顶部。
- 邮箱下方横向展示五个平台，固定顺序为：QQ、抖音、QQ群、小红书、Bilibili。
- 每张渠道卡片从上到下包含：平台 Logo + 平台名称、二维码、账号/群号。
- 宽屏横向排列；空间不足时等宽换行；手机可单列或双列，但二维码与最长账号不得溢出。
- 卡片不宜过大，二维码必须清晰可扫；平台名称和账号在不依赖 Logo 的情况下仍可阅读。
- Logo 旁已有平台名称时，Logo 使用装饰性空 `alt`；二维码使用明确的可访问名称。
- 平台业务值不得在公开模板里写死。联系数据结构为五项平台记录，每项至少包含：
  - `platform`: `qq | douyin | qq_group | xiaohongshu | bilibili`；
  - `account`: 对应账号或群号；
  - `qrCodeAssetId`: 私有二维码资产引用。
- 平台显示名、固定排序和 Logo 由平台枚举元数据统一映射，不由管理员上传或任意改名。
- 管理入口继续在 `/admin/site/content` 的“官方联系方式与防诈骗提醒”分区内扩展；不得在 `about.vue` 写五个固定业务值。
- 前向迁移必须保留现有邮箱，并把已有 QQ、抖音值迁入新结构；其它平台和二维码可为空，不能因升级导致公开页 500。
- 只有账号与 READY 二维码公开派生都存在时才显示完整平台卡；后台明确提示缺少哪一项。
- 后台始终显示五个平台固定槽位；公开端只显示信息完整的平台，因此迁移后、补齐真实数据前可以少于五张。T05 最终验收时再要求五个平台真实数据全部完整。
- 二维码源图私有保存；公开图使用专用无水印、保持方形、不裁切的派生用途。
- 二维码接受 PNG、JPG/JPEG、WebP，允许方形、横图和竖图且不超过 20 MB；服务端保留完整私有原图，并复用内嵌 FFmpeg Lanczos 按比例把原图完整容纳到 640×640 白色画布内，不裁切内容，再由现有 `contact-qr-v1` 配方生成 320/640 PNG 公开图。任一边小于 64 px 的图片仍拒绝，避免把明显不具备可读性的位图伪装成二维码。
- FFmpeg 适配不会恢复原图不存在的细节；后台在处理期间和失败后都要给出明确中文反馈，并允许沿用现有媒体重试入口。
- 公开端只出现两个完整渠道时，卡片保持与五渠道相同的阅读尺寸并左对齐，不允许被拉伸成占满整行的两张大卡。
- 五个平台 Logo 的来源、商标归属和使用说明在实现记录中登记；不新增图标依赖。

### FR-03 · 委托邮件估价标准模板

- 在 `/admin/site/content` 当前“委托常见问题”数据中追加一条固定 FAQ：
  - 问题建议文案：`邮件估价咨询可以按什么格式填写？`
  - 回答至少包含：角色名、委托装型、身高/体型、设定图、希望实现的细节、期望时间和其它说明。
- 该项通过新的前向 SQLite 迁移加入，使用固定 UUID，重复检查时不得产生第二条。
- “固定”只指迁移使用稳定 UUID 并保持幂等；迁入后它仍是现有 FAQ 列表中的普通项目，管理员可以编辑、排序或删除，迁移不会在每次启动时重新插入。
- 迁移不得覆盖管理员已有 FAQ；如需提高当前最多 8 项的上限，应同步 Schema、管理提示和测试。
- 公开委托页继续消费既有 FAQ 投影，不新增第二个模板组件。
- 不发送邮件、不接 SMTP、不上传设定图、不收集访客输入；这些属于下一轮迭代。

### FR-04 · 三个公开列表按设定名称搜索

- `/works` 按 `work.characterName` 搜索。
- `/adoptions` 按 `work.characterName` 搜索。
- `/returns` 按 `return_characters.name` 搜索；同一设定的所有已发布返图均可命中。
- 公开查询参数统一为 `q`：trim 后 1～100 字；缺失或 trim 后为空等同未搜索；数组、非字符串或超过 100 字的值收敛为受控“搜索条件无效/无匹配”状态，并提供清除链接，不抛 500，也不退化为展示完整列表。
- 匹配为不区分大小写的包含匹配；规则应抽取为共享纯函数并回接后台作品搜索，避免公开端与后台出现两种行为。
- 搜索框使用 GET 语义，SSR 可直出，无 JavaScript 时仍可提交。
- 搜索框不再在输入框上方重复显示“按设定名称搜索”；组件继续保留等价的可访问名称，输入框占位文字承担可见提示。
- `/works` 与 `/adoptions` 在宽屏把搜索和筛选放在同一紧凑工具栏；空间不足时按控件组安全换行，不允许横向溢出。`/returns` 没有分类筛选，只保留同尺度的紧凑搜索行。
- 新搜索会回到第 1 页；分页链接保留 `q` 和当前筛选。
- 作品筛选与领养方式筛选切换时保留 `q`。
- 返图搜索结果仍按 seed 随机；同一次搜索的分页保留 seed，新关键词不继承旧 seed。
- 空态区分“站点暂无内容”和“该设定名称无匹配”，并提供清除搜索的普通链接。
- 搜索词不写入访问统计、不进入持久日志、不返回到错误正文。

### FR-05 · 最新动态

- 新增公开一级路由 `/updates`，导航文字为“最新动态”，位于“关于我们”之前。
- 首版动态类型固定为：参展资讯、掉落预告、开单通知、其它。
- 类型与存储枚举固定映射为：参展资讯 `event`、掉落预告 `drop`、开单通知 `commission_open`、其它 `other`。
- 每条动态至少包含：稳定 ID、类型、标题、纯文本正文、发布状态、发布时间、创建/更新时间与逐条资源版本。
- 公开页只显示 published 项，按发布时间倒序；首版直接在列表展示正文，不新增详情路由。
- 首页在“当前领养”之后、页脚之前把最近 3 条已发布动态作为最后一个内容模块展示；没有动态或查询失败时受控隐藏该区块，不拖垮 Hero 与作品展示。
- 首页摘要只显示“最新动态”标题，不再增加“工作室通知”眉题；标题字号、字重和标题/“查看全部”的基线与“精选作品”“当前领养”等首页模块一致，上下间距使用同一首页节奏，不制造额外的大块留白。
- 首页摘要与 `/updates` 共用同一动态卡片：白底圆角矩形、克制边框和类型前缀圆点；类型颜色只作辅助，类型文字仍必须可读。首页卡片可截断长正文，完整列表保留全部纯文本。
- `/updates` 在列表上方提供与作品页相同视觉的类型筛选条：全部、参展资讯、掉落预告、开单通知、其它。筛选使用普通链接和 `type` 查询参数，SSR、重载与无 JavaScript环境均可用；筛选只改变公开列表呈现，不改变发布状态或首页最近三条的全类型排序。
- 管理员可以新增、编辑、发布、下架和删除动态；未发布内容不进入公开 API、SSR、sitemap 或首页。
- 首次发布写入当前 `publishedAt`；下架后重新发布时更新为本次发布时间，使公开倒序与“最新”语义一致；仅编辑已发布正文不改变发布时间。
- 后台使用独立 `/admin/updates` Tab 与 `updates` 表；不在 `/admin/site/content` 增加第二套动态入口。
- 首版不含图片、附件、富文本、定时发布、外部链接按钮、详情页或正文搜索；只提供上述固定类型筛选。

## 5. 路由与接口契约

### 保留路由

- `/commission`、`/adoptions`、`/works`、`/returns`、`/about` 全部保留。

### 新增公开路由

- `GET /updates`：最新动态列表页。
- `GET /api/public/v1/updates`：只返回已发布动态。
- `GET /api/public/v1/home-aggregate`：增加可降级的 `latestUpdates` 最近三项。

### 扩展公开查询

- `GET /api/public/v1/works?q=<设定名称>`。
- `GET /api/public/v1/adoptions?q=<设定名称>`。
- `GET /api/public/v1/returns?q=<设定名称>`。

### 扩展管理接口

- 联系方式继续使用 `PUT /api/admin/v1/site/home/content/contact`，请求结构扩展为五个平台记录与二维码资产引用。
- 动态使用独立 `/api/admin/v1/updates` 资源接口；不实现方案 A 的分区写入口。

## 6. 非目标

- 不修改已有作品、返图、领养详情路由或发布语义。
- 不把常规领养和展会掉落拆成新数据模型。
- 不做模糊拼音、同义词、标签、物种或正文全文搜索。
- 不让管理员编辑平台 Logo、平台名称或排序。
- 不把二维码原图直接公开，也不对二维码加作品水印。
- 不在本轮实现 SMTP、邮件模板发送、估价表单或用户数据收集。

### FR-06 · 首页轮播预验收修正

- 自动轮播固定开启、每 10 秒一张，继续尊重 `prefers-reduced-motion`，页面隐藏时停止，用户可用明确的暂停按钮手动暂停。
- 鼠标停留在大面积 Hero 上或控件获得焦点时不得让轮播长期停住；否则桌面访客会误以为自动轮播失效。无障碍暂停仍由可见暂停按钮提供。
- 手动上一张、下一张、圆点、键盘与触控行为保持不变；自动切换只渲染当前图片，不预下载隐藏项。

### FR-07 · T17 首轮用户验收视觉与交互修正

- Hero 自动切换及上一张、下一张、圆点、键盘、触控切换都使用平滑过渡，不得像整页刷新一样瞬间替换。过渡优先使用 `transform` 与 `opacity`，只在切换期间短暂保留离场项，不预下载后续隐藏图片；`prefers-reduced-motion` 下取消过渡。
- 首页统一业务入口区标题由“委托与领养”改为“委托投递”；下方独立“当前领养”区保持不变。
- 首页“当前领养”和“最新动态”的“查看全部”文字与箭头常态均使用同一品牌蓝，并保留清楚的 hover/focus 状态。
- `/about` 的“防诈骗提示”使用无卡片排版，并成为与“工作室 / 制作范围 / 联系”同级的内容 section；标题字体、字号、字重、行高和与前一模块的间距必须复用完全相同的 section 规则。
