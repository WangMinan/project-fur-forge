# 规格说明：后台录入已有委托

## 状态与来源

- 日期：2026-11-16；本地实现与自动验证完成，待人工验收；用户随后授权实现、测试和本地预览，禁止生产部署。
- 用户要求：在 `/admin/commissions` 录入 QQ 等渠道的已有委托，与官网申请统一查看；补录不走 SMTP。
- 用户补充：目前数量很少、不需要 Excel；都是自设委托，不纳入排期收款；手机号或 QQ 判断人员重复，提示冲突但确认后可继续，因为同一人可能再次定做。
- 上一轮18项建议获用户总体采纳。下文具体长度、日期校验、并发与重试语义为实现所需的细化，不代表用户逐字段指定。
- 现有基线：[需求3](../../需求3-站点业务简化与委托投递/requirements/SPEC.md)、[需求4](../../需求4-站点视觉升级与内容合规/requirements/SPEC.md)、[需求5](../../需求5-委托邮件通知与站点配置/requirements/SPEC.md)、[需求9](../../需求9-管理列表风格统一/requirements/SPEC.md)、[需求15](../../需求15-确认弹窗与快速检查/requirements/SPEC.md)。

## 目标与非目标

管理员可以逐条录入、补齐和纠正线下收到的自设委托，统一查找、处理和导出制作单，清楚识别申请来源及邮件是否适用。

本期不做 Excel/CSV 导入导出、聊天识别、批量操作、客户档案、自动合并、排期、收款、合同、制作进度、领养、公开查询、持久草稿或任意邮件发送。现有制作单 PDF 导出保留。

## 1. 来源与字段

记录来源固定为“官网提交”或“后台录入”，创建后不可互相转换。现有数据迁移为官网提交，不推断未记录的渠道。后台录入要求渠道为 QQ、微信或其他；选择其他须填写渠道名称。

| 字段 | 后台录入规则 |
| --- | --- |
| 称呼 | 必填，去除首尾空白，1–50字 |
| 来源渠道 | 必填；其他渠道名称1–50字 |
| 物种 | 可空；填写时1–50字 |
| 手机号 | 可空；填写时沿用+86大陆手机号校验 |
| QQ | 可空；填写时沿用5–12位非零开头数字校验 |
| 其他联系方式 | 可空，纯文本1–200字，可记录微信、邮箱、海外联系方式 |
| 联系方式整体 | 手机、QQ、其他联系方式至少一项非空；不要求渠道与填写的联系方式一一绑定 |
| 身高、体重 | 可空；填写时沿用80–250cm整数、20–300kg最多一位小数 |
| 设定图 | 可空，最多1张JPEG/PNG/WebP，最大20,000,000字节，边长64–12000px |
| 内部备注 | 可空，最多2000字，沿用现有纯文本规则 |
| 原申请日期、历史处理日期 | 可空，按北京时间录入日历日期，不伪造时分秒 |
| 状态 | 待处理、已接受、已拒绝，默认待处理 |
| 线下确认 | 成年已确认、资料用于委托处理已确认，默认未确认 |

空值统一显示“未填写”，不生成占位手机号、零身高或占位图片。其他联系方式不做模糊人员匹配，不解析成新账户模型。官网申请原必填规则与公开请求契约保持。

## 2. 人员冲突与保存防重

### 人员冲突：可确认继续

- 新建补录时，按规范化后的手机号或 QQ 精确匹配全部现存申请，涵盖所有来源和三种状态；任一相同即命中，不要求两者同时相同。不按昵称、物种或其他联系方式猜测人员身份。
- 手机和 QQ 分别命中不同记录时，展示全部命中并注明匹配原因，不据此认定这些记录属于同一人。
- 提示显示申请编号、称呼、状态、来源、进入系统时间和匹配原因，可在新窗口查看详情；不在通用错误、URL、日志中回显联系方式。
- 管理员可返回修改，或选择“确认继续录入”。确认只允许本次申请继续，不合并、不覆盖、不更改旧申请状态。
- 默认聚焦返回修改。联系方式改变、命中集合或命中记录版本改变后，之前确认失效，重新提示；最终写入前服务端复核，不能只依赖前端检查。
- 修改补录记录的联系方式时使用同一规则，排除自身；联系方式未改变时，不为单纯备注或状态修改重复弹冲突。
- 没有手机号和QQ、仅其他联系方式时，可正常保存，并提示“未填写手机号或QQ，无法自动核对重复申请”；不承诺此时已完成查重。
- 同一人可有多条申请，包括经管理员确认后的多条待处理申请；联系方式不是申请唯一键。

### 保存防重：不能确认后重复建单

- 同一保存操作的重复点击、超时重试和响应丢失后的重试，只产生一条申请和同一个编号，适用于无图片记录。
- 重试返回已保存结果，不因其刚产生的记录反过来触发人员冲突。已成功操作不能换一份内容复用其身份；要录第二笔须发起新的录入操作。
- “保存并继续录入”只在服务端确认成功后清空，生成新的操作身份；失败保留当前输入。结果未知时先核对同一操作结果，不能盲目当成新申请提交。
- 本期不做跨刷新持久草稿；页面重开后用列表核对已保存记录，重新建单仍经过联系方式冲突提示。

### 官网提交保持原拦截

官网仍在同手机号存在任一来源的待处理申请时拒绝新提交，不提供访客绕过按钮；已接受/已拒绝历史不阻断官网新提交，也不新增官网QQ拦截。需要并行申请时由管理员核对后录入。此规则不妨碍用户日后再次委托。

## 3. 时间、状态与确认

- 系统创建时间始终代表进入系统时间；官网为提交时间，后台为录入时间。原申请日期不得回写系统时间。
- 列表按系统创建时间倒序、ID稳定兜底，不加入用户可选排序。时间列官网显示“提交”，后台显示“录入”；后台另显示“原申请：YYYY-MM-DD / 未填写”。详情分别列出这些时间。
- 历史处理日期仅已接受/已拒绝时填写，可留空；原申请日期和历史处理日期不得晚于北京时间今日，两者都存在时后者不得早于前者。待处理不保存历史处理日期。
- 系统处理时间与处理管理员记录实际操作；历史处理日期独立保存，未知不填今天。改回待处理清除当前处理信息及历史处理日期，保留无PII的操作审计。
- 后台可直接录入已接受/已拒绝；接受（含直接创建为已接受）前，两项线下确认必须已确认。未确认可保存待处理或已拒绝；已接受时不可撤销确认，须先改为待处理。
- 两项确认明确是管理员根据线下沟通记录，不表示申请人曾在官网勾选，不生成追溯性的官网确认或法律证据。
- 资料缺项本身不阻止接受，但详情明确展示缺项；无设定图则制作单不可导出。

## 4. 页面与编辑

- 列表页头新增“录入申请”，进入 `/admin/commissions/new`，沿用现有后台页头、表单、按钮、下拉与确认弹窗。
- 新建提供“保存并查看”“保存并继续录入”；前者进入详情，后者保留录入页面并清空业务字段，状态重置待处理、确认勾选重置，渠道默认QQ。清楚反馈保存的申请编号。
- 录入及编辑页面支持现有桌面/窄屏交互，不引入表格内编辑或多步向导。
- 2026-11-16用户追加视觉要求：与现有作品编辑页同风格。使用卡片内标题、共享字段样式及顶部返回/标题/保存栏；主栏申请资料与处理卡、侧栏设定图，1280px起使用同一24rem侧栏与20px列间距；字段网格768px起两列，窄屏单列，标题/标签/输入/卡片边缘对齐。
- 后台录入记录可改称呼、物种、联系方式、渠道、日期、身高体重、设定图、备注、状态和线下确认；不可改记录来源、系统编号、实际创建时间。官网只保留原状态/备注编辑能力。
- 保存忙碌时禁重复操作；校验失败定位具体字段；失败保留输入；版本冲突提供重新载入或保留输入，不能静默覆盖。
- 未保存离开提醒复用现有组件；刷新/关闭页面保留浏览器原生保护；会话失效不阻断回登录。业务资料和上传凭据不写localStorage/sessionStorage。
- 表单标签常驻，必填/可选、单位与错误说明关联控件；普通成功/错误使用就近持久反馈，不弹“知道了”。“保存并查看”为主行动，“保存并继续录入”为次级行动；成功编号不能只在短暂Toast中出现。
- 冲突确认复用AdminConfirmDialog，具备标题、焦点约束、Escape/取消与焦点归还，不嵌套弹窗。独立操作命中区按项目默认至少44×44 CSS px，hover不作为触控唯一反馈。
- 上传显示真实字节进度，校验和保存显示真实阶段或不确定进度，不伪造百分比；无图、图片读取失败、上传过期与会话过期提供各自准确说明。结果未知使用持久状态，未确认成功前不清空表单。

- 2026-11-16完整E2E追加：详情的编辑/导出操作始终属于同一个靠右操作组，导出加载、失败不改变其相对排列；加载失败的设定图可重试。列表窄屏维持既有导航页头标题/分割线对齐，刷新移入筛选区，桌面操作位置保持。

## 5. 列表、编号与邮件

- 两种来源共用现有列表和详情；来源列显示“官网提交”“后台录入 · QQ/微信/其他渠道名”。筛选项为全部来源、官网提交、后台录入·QQ、后台录入·微信、后台录入·其他，默认全部来源。
- 保持全部状态默认值、状态筛选、昵称/物种/编号搜索、失焦应用搜索和分页。新增来源筛选与现有状态筛选可组合；筛选变更回第一页，清除恢复全部状态/来源；筛选可进入URL，搜索词不可。
- 联系方式不加入列表DTO、列或搜索；详情按认证权限查看。窄屏卡片保留来源、日期和全部操作。
- 沿用唯一 `DD-…` 系统编号；管理界面及内部制作单使用“申请编号”。内部字段可保留 `receiptCode`，不为改名更改公开成功响应或官网回执文案。
- 后台录入邮件状态固定“无需邮件”，不创建收件人快照、发送任务或失败记录。详情用简短说明替代重试控件；直接调用邮件重试接口也必须拒绝后台录入记录。
- 修改渠道、资料、状态、SMTP开关、内部收件邮箱及任务恢复都不会使后台录入进入邮件队列。官网现有邮件行为和历史状态保持，不补发历史记录。

## 6. 图片、制作单与删除

- 复用私有委托图片校验、存储和管理同源预览；上传由认证管理入口创建并绑定管理员/用途，不借匿名上传绕过管理权限。不产生公开派生物、私有GET签名或重定向。
- 详情默认1280预览，管理员显式点击原图在新窗口查看。无图片显示缺图状态，不发送必然404的图片请求。
- 可补传、替换或移除图片。新图完成验证且资料保存成功才切换引用；失败/冲突保留原图。移除已保存图片须确认；旧图与未消费上传沿用精确、可恢复清理机制，不能提前删原图或制造不可回收孤儿。
- 已接受且有可用设定图时可导出既有制作单；缺少其他字段显示“未填写”。无图时不提供导出操作并说明补图要求，服务端同样校验；资料长文本换行，超出资料页时续页，最后一页仍为完整设定图；来源、原申请日期、录入时间使用真实标签，不能把录入当成原提交。
- 两种来源都仅在已拒绝状态提供单条删除，沿用盘点、确认、精确删除、lease与邮件协调。无图记录合法，不能被当成图片关系损坏而永远无法删除；有图删除相关私有对象及关联数据。
- 不新增自动删除。既有保留候选按系统创建/处理时间工作，不把补录历史日期误接到清理期限。
- 本轮仅实施本地功能及虚构数据验证，不授权任何生产图片或数据库删除。

## 7. 覆盖旧契约与数据兼容

| 既有规则 | 本需求局部覆盖 |

## 验收标准

以下为验收契约；本地自动验证及边界见 [STATE](../STATE.md) 和 [交接](../implementation/notes/2026-11-16-LOCAL-IMPLEMENTATION.md)，不代签人工或生产验收。

| 编号 | 验收场景 |
| --- | --- |
| A01 | 最低资料及完整资料均可保存；缺全部联系方式/非法非空值被拒绝；官网仍要求完整资料 |
| A02 | 手机或QQ命中任意来源/状态均提示；分别命中不同记录完整展示；取消不写入，确认可另建且旧记录不变 |
| A03 | 联系方式/命中集/版本变更重新确认；修改排除自身；仅其他联系方式明确无法自动核对 |
| A04 | 连点、无图重试、响应丢失、并发同一操作均只有一条记录；独立确认的新操作可创建第二笔 |
| A05 | 官网同手机号pending拦截涵盖后台记录；accepted/rejected不拦截；并发官网请求不能双建 |
| A06 | 三状态直接录入、两项确认门槛、日期未知与日期校验、真实系统时间/排序正确 |
| A07 | 后台可补改、官网不可越权改资料，版本冲突、忙碌、失败与离开保护正确 |
| A08 | 来源/状态/搜索组合、分页、清除、返回导航、窄屏卡片与编号显示正确 |
| A09 | 后台无邮件意图且重试接口拒绝；配置变动、重启恢复不误发；官网邮件回归通过 |
| A10 | 无图、补图、替换、移除、失败/冲突/中断清理、同源预览及原图权限符合边界 |
