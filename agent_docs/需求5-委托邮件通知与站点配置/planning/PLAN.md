# 计划：委托邮件通知与站点配置

## 执行结论

- 2026-09-06：用户同意 SPEC 与方案并授权在当前分支实施，T01～T08 本地范围已完成。
- 保留一个常驻 app 和当前 SQLite；使用最小持久通知记录与 app 内后台执行，不新增队列服务或部署拓扑。

## 执行顺序

### 1. 配置与数据边界

- 核对 `server/utils/runtime-config.ts` 与 `config/` 配置注册方式，补齐 SMTP 服务端加载、脱敏校验，以及 `docker-compose.yaml` 环境注入；后续同步 `.env`、`.env.example`、`.env.compose.example`。
- 默认使用用户给定的 465 隐式 TLS；若使用 587，则要求 STARTTLS，不明文降级。实施选定 SMTP 客户端前查阅其官方文档及 QQ 官方帮助，核对附件大小与错误语义。
- 增加 `site_content` 内部收件列表及通知记录前向迁移、模型与约束。初始化默认值只运行一次，保护空列表与自定义配置。
- 把通知取消/清理纳入现有委托删除流程，并先定义与发送领取的互斥边界。

### 2. 管理配置与公开隔离

- 扩展 contact 管理 Schema、DTO、分区更新列、`useAdminSiteContent` 与 `SiteOfficialChannelsCard.vue`，沿用当前分区版本和安全入口。
- 内部列表独立于公开 `email`、`officialChannels`；检查 `getPublicSiteContent` 显式投影及首页聚合 DTO，禁止顺手展开内部字段。
- 内容页及导航改名为“站点配置”，同步加载、错误和可访问名称。公开页面不编辑。

### 3. 委托事务与发送

- 检索 `createCommissionSubmission` 所有调用方，在共同创建事务内写入通知意图；不在路由单独补丁，也不把 SMTP / OSS I/O 放入事务。
- repository 管理逐收件人唯一约束、领取、尝试次数和结果；service 映射正文与可信附件身份；runner 通过现有私有存储入口读取设定图并发送。
- 评估复用 `getCommissionDesignReference`、`MediaStorage.getPrivate`；不要为邮件再建一套 OSS 客户端或公开预览链。
- 默认独立发送每个地址；纯文本模板足够。发送失败不能改变委托状态或公开成功响应。

### 4. 恢复与最小后台反馈

- app 启动恢复待发任务，运行中按到期时间处理重试；关闭时清理调度器，测试默认禁止真实发信。
- 默认单个发送并发，3 分钟领取由 30 秒心跳续租，SMTP 连接/问候各 15 秒、socket 空闲 30 秒超时，临时失败最多尝试三次，重试间隔先取 1 分钟、5 分钟；认证错误、明确永久拒绝、附件超限不盲目重试。以上为初稿工程默认值，实际限制核对后再校准。
- 使用有期限的领取避免两个执行入口重复处理；SMTP 接受后落库中断无法消除所有重复，保留稳定 Message-ID 和委托编号供辨认，不将其视为收件端去重保证。
- 在现有委托列表/详情加入最小通知摘要、按收件人的结果和未成功项重试入口；后台重试复用 Host、Session、Origin、CSRF、no-store 和 body 校验。
- 移除收件人取消尚未进入网络发送的记录，包含已领取但尚未发送的项；领取后、发送前再次检查取消状态、当前收件列表与委托是否仍存在，并与删除流程协调。单纯关闭 SMTP 只暂停，删空列表则取消，重新添加地址不恢复取消项；已进入网络发送的邮件不能保证撤回。

### 5. 验证与交接

- 普通实现运行 lint、typecheck、受影响 core；本需求涉及 runtime/config，追加 build。优先扩展既有集成测试，不新建无关测试框架。
- 自动测试使用虚构邮箱/委托和本地 SMTP 替身，不使用用户真实资料或真实收件箱。
- 浏览器覆盖六档后台视口、键盘/焦点、列表错误与冲突；对用户侧做原有表单流程和文字不变回归。
- 实施完成后进行受控真实 SMTP 联调，验证最大附件、两个收件箱、容器配置注入；联调邮件属于向真实人员发送信息，本轮已获两封虚构测试邮件授权，用户进一步限定只发给自己，已完成自发自收；不测试默认客服/景宸收件箱。
- 交付时分别标记代码、自动验证、人工收件、部署状态；生产操作依旧按 [部署文档](../../../docs/DEPLOYMENT.md) 与发布手册执行。

## 技术决策

- 使用 Nodemailer 10.0.0 及其内置类型，无额外类型或队列依赖；不手写 SMTP、TLS 或 MIME。官方文档与 Linux 声明证据见产物索引。
- 收件列表暂定一个 JSON 数组列，复用 contact 分区保存；通知记录使用独立小表，避免每个委托行容纳可变数量投递结果。
- 只存委托引用与通知状态，发送时读取业务文字和私有图片，不建立正文/附件副本缓存。
- 配置问题只影响通知可用性；不能把 SMTP 检查加成公开站或委托提交的硬性可用性依赖。

## 实施校准

- 保留旧库委托列表只读兼容；旧客户端 contact 更新省略新字段时保留已有内部列表，不意外清空。
- 0052 另加投递时策略和持久删除标记，用于区分历史未通知、停用期和跨进程删除；详见模型。
- `transport.close()` 对非池 SMTP 连接不保证中止正在发送的 socket，因此不使用提前返回的 Promise.race 冒充取消；使用库的网络超时与领取心跳，等待真实发送结果。
