# 地基：后台录入已有委托

业务权威见 [SPEC](../requirements/SPEC.md)。复用委托领域，不另建客户或订单系统。

## 模块边界

- `app/pages/admin/commissions/` 与现有管理组件：录入、来源筛选、补改和状态展示；官网页面保持原提交行为。
- `shared/schemas/commission.ts`、邮件Schema、contracts：区分来源、可空字段、冲突和重试契约，不把后台宽松规则套到公开请求。
- repository 管 SQL、事务内冲突复核、唯一性与lease；service 管校验、DTO、业务事务；runner 管持久清理和副作用；route 管认证、Host、Origin、CSRF及限流。
- 图片、邮件、制作单、保留候选与删除都是必要调用方，不能只改新建表单。

## 存储与身份

- 同一个 `commission_submissions` 集合承载两类来源；申请ID/编号唯一，手机号/QQ只作人员匹配。
- 创建操作的重试身份与人员匹配分开；不能用手机号作幂等键。
- 后台可多条pending，官网仍有同手机号pending拦截。调整原全局索引必须同步公开并发保护。
- 前向迁移保留旧数据；系统时间、历史日期、线下确认不可混写。字段提案见 [模型](../models/README.md)。

## 安全与授权

- 所有新增写入口仅管理Host、认证会话可用，并沿用Origin、CSRF、限流、版本和no-store约束。
- 查重参数通过请求体传输；手机号/QQ不放URL、日志、普通错误、截图或真实fixture。
- 冲突确认只解除本次业务查重阻止，不解除权限、校验、版本或重试防重。
- 图片全程私有，同源字节预览；接入既有清理/recovery，保证失败时旧引用可用。
- 已获本地实现、测试和预览授权；不构成生产录入、删除、迁移、邮件测试或部署授权。
