## 目标

1. 新自设委托成功保存后，后台队列照常显示，并向工作室配置的每个内部邮箱发送通知，减少遗漏。
2. 管理员在 `/admin/site/content#content-contact` 增加、修改和删除通知收件邮箱，数量不写死为两个。
3. `/admin/site/content` 从“文案配置”改为四字名称“站点配置”，覆盖标题、导航、加载和错误等相关后台文字。
4. 将 SMTP 配置完整接入本地与容器运行环境；用户提供的授权码只进入秘密配置。

## 非目标

> 本轮追加授权例外：用户允许 `/licenses` 的开源声明同步，并已精简其导言；保留这一修改。其它用户侧业务文案和隐私政策仍保持不变。

- 不改变用户侧 UI、文案、隐私政策、申请字段、上传数量与限制、交互和公开 API 契约。
- 不给申请人发确认邮件，不发送处理状态变更通知，不自动接单、建作品或报价。
- 不做历史委托群发、任意邮件发送、营销订阅、邮件正文编辑器或通用通知中心。
- 不增加后台 SMTP 密码编辑框，不把内部邮箱展示为新的公开联系渠道。
- 本轮不执行 Git 提交/推送或生产发布；真实联调按追加授权仅向用户自己的邮箱发送两封虚构测试邮件。

### 2. 方案默认行为

以下为本次梳理补齐的可评审默认方案，并非用户逐项指定。用户已同意下述方案。页名为“站点配置”；收件列表为空代表暂停后续邮件通知；通知失败可恢复；无历史补发。后续如调整须同步本规格及计划。

### 3. 收件列表与后台页面

- 初始包含上述两个邮箱。列表支持一个、两个及更多地址，逐行新增、编辑、删除，保存后持久化，刷新与重启不丢失。
- 每行只要求邮箱地址，不为两位现有接收者硬编码槽位、角色或专属字段；接受有效邮箱，不额外限定 `qq.com` 域名。
- 保存前去除首尾空白并校验完整单个邮箱；拒绝空行、换行注入、多个地址混在一行，以及重复地址。QQ 地址按大小写不敏感识别重复；其它地址沿用明确的规范化规则，不能静默合并不同邮箱。
- 可保存空列表，后台明确提示“未配置委托通知邮箱，新投递仅在后台列表中保存”。不得在空列表时偷偷恢复默认邮箱。
- 表单沿用现有草稿、保存成功、错误和版本冲突反馈；不得因编辑邮箱破坏 QQ / QQ群二维码或公开联系邮箱。
- 收件目标以投递时快照为准；新增地址不补发历史委托，已成功发送的记录不因配置保存重发。删除地址时取消该地址尚未进入网络发送的通知，列表删空对全部移除地址执行同一规则；已经进入 SMTP 发送的邮件无法保证撤回，后台应说明这一边界。任务领取不等于网络发送开始，领取后必须在发送前复核取消状态、当前收件列表及委托是否仍存在。
- 页面 URL、`#content-contact` 锚点与其它管理分区功能保持；“文案配置”相关活跃后台文字统一为“站点配置”，不改历史文档来伪造过去名称。

### 4. 触发与邮件内容

- 仅真实新建且事务提交成功的自设委托触发；上传、预览、校验失败、被拒绝的重复投递、管理修改状态和查看列表不触发。
- 为投递成功当时的每个收件地址建立通知；逐地址独立发送，避免一个无效地址阻止其它人收到，也避免在收件头公开整个内部列表。
- 主题固定为 `【有点小狗】收到新的自设委托，请及时处理`；发件显示名默认“有点小狗工作室”。用户文字不进入主题、发件人或 Reply-To。
- 正文包含投递编号、提交时间（北京时间）、称呼、物种、完整手机号、QQ、身高（cm）、体重（kg），附管理详情链接。体重按现有存储单位正确还原，不暴露内部十分位值。
- “全部文字信息”指全部用户填写的业务文字。两项勾选仍按现有服务端 `true` 校验，邮件不再重复提交确认及接单免责声明；不另建法律证据系统。上传 token、蜜罐、版本号、私有 Key、内部备注和管理审计不属于邮件内容。
- 默认纯文本正文；若采用 HTML，必须转义全部用户文字并提供纯文本版本。后台链接以 `ADMIN_BASE_URL` 生成，登录要求保持；不得把手机号、QQ、授权 token 或附件签名地址塞入 URL。
- 附件使用这笔申请的 READY 私有设定原图，保持原始字节与 MIME；文件名由投递编号和可信扩展名生成。不另附 PDF，不压缩降质、不生成公开链接。
- 附件读取失败或服务端拒绝邮件大小时，该收件人的通知不得标为成功，也不得静默改成无附件成功；保留后台投递和可操作的失败状态。

### 5. 成功、失败与恢复

- 对申请人而言，成功仍表示委托已保存；API 不等待 SMTP 网络发送，也不暴露邮件状态。邮件断网、认证失败、收件拒收或附件错误不回滚已保存委托，不要求申请人重复投递。
- 通知意图与新委托在同一事务持久化，实际网络发送在事务外；避免“已保存但进程退出后永远漏通知”。事务本身失败沿用既有失败语义。
- 使用逐收件人状态，成功项不随失败项的重试再次发送；每位收件人最多尝试两次（首次加一次自动重试），首次临时失败后等待 60 秒；永久失败停止自动重试，管理员可在修正问题后重试未成功项。
- 2026-09-09 追加授权：SMTP 建连、问候及连接空闲超时均为 600 秒，不是整次发送的总计时。停止时取消在途连接，Nitro 超时 4 秒、容器宽限 5 秒，优先快速重启；已开始传输但结果未确认的停止/过期任务记为 `failed + UNKNOWN`，核实收件箱后人工决定是否重试，不自动补发。未进入传输的任务按两次上限恢复。
- 后台列表显示简明通知状态，详情提供失败原因类别与重试反馈，不建设额外通知中心。
- SMTP 服务器接收只表示接受投递，不等于进入收件箱或已读。SMTP 确认与本地落库之间中断可能重复投递，不承诺严格“恰好一次”；邮件始终带相同委托编号以便辨认。
- 关闭 SMTP 或没有收件地址时仍允许委托保存，并显示通知未启用或未配置；这期间的新委托不在重新启用后自动补发。仅关闭 SMTP 时，已有待发记录暂停；删除收件地址（含列表删空）则取消对应未发送记录，重新添加地址不恢复已取消项。重新启用后只恢复仍有效的暂停任务，继续遵守资料删除规则。
- 收件人部分成功时，后台应能区分成功和失败，不能只显示整笔申请“成功”。

### 6. 配置与数据模型契约

- SMTP 由服务端环境配置控制：启用状态、Host、端口、TLS 模式、账号、授权码及发件人；实现时写入本地 `.env`，同步两个示例的键与注释。
- 示例不含真实授权码；真实账号、Host 与端口可用于本地配置，示例账号使用示意邮箱。收件列表保存在数据库，不依赖两个固定环境变量。
- 运行时加载与校验、实际 Compose 注入必须同步；启用但缺必填项或 TLS/端口不匹配时给管理员/操作员明确脱敏配置错误，不能使公开委托不可用。TLS 不允许关闭证书校验或明文降级。
- 扩展管理 contact DTO、更新 Schema 和存储；公开 contact DTO 字段和值保持原样，邮件凭据不进入任何 DTO。
- 新增最小逐收件通知记录，唯一身份为 `submissionId + recipient`；字段详情由 [模型说明](../models/README.md) 管理。
- 仅新建前向迁移；首次种入默认列表，不覆盖已有配置。受控删除委托时处理关联待发任务，不继续读取已删资料；已发邮件副本由工作室内部管理。
