## 权威顺序

每个需求目录内按以下顺序读取：

1. `foundation/README.md`：产品与不可突破边界；
2. `requirements/SPEC.md` 与适用媒体政策：业务、数据和安全契约；
3. `planning/PLAN.md`、`planning/DATA-MIGRATION.md`：技术路线、顺序和破坏性停止点；
4. `.design/`：公开端与管理端体验；
5. `models/README.md`：目标持久模型和 DTO 投影；
6. `implementation/TASKS.md`：该需求唯一任务和勾选权威；
7. `STATE.md`：当前阶段、阻断项和下一步。

`materials/`、历史原型、dated notes、旧 Review 和截图只能说明当时事实，不能覆盖活文档。需求1的 `planning/FUTURE-ITERATIONS.md` 不是实施授权。

跨需求发生冲突时：

1. 后续需求只在其 SPEC 明确写出的范围内覆盖旧行为；
2. 安全、隐私、媒体、Host、部署和质量基线若未明确改变，仍以需求1为准；
3. 当前编码必须同时阅读需求1基线和需求3活文档，不能只看历史实现笔记。

## 执行纪律

- 所有代码、文档、Review 和修复通过独立分支与 PR 合入 `main`，禁止直接在 `main` 提交或推送；
- 契约变化先同步 foundation、SPEC、PLAN、models、TASKS 和 STATE，再改代码；
- 后端/数据/安全 → 前端 → 本地破坏性演练 → 新上下文独立 Review → 用户验收 → 生产执行；
- 同一实现者不得为自己的实现代签独立 Review；
- 不删除或清空 `.env`，不重写已执行历史迁移，不把 Secret、PII、真实图片或完整 Object Key 写入仓库、日志或截图；
- 需求3虽然授权永久删除，但清理工具仍必须默认 dry-run、精确枚举、强确认并在 DROP TABLE 前完成对象验证；
- 自动化不能替代真实浏览器、真实手机、用户验收或生产控制台核对；
- 不把功能工程完成、PR CI、独立 Review、用户验收、代码冻结、生产清理或正式发布互相代签。
