## 4. 直接在 main 上的执行纪律

由于不再切分支，所有写入必须串行：

1. 开始前读取远端最新 `main`，确认工作区干净且没有另一个 Agent 正在写；
2. 后端任务先提交契约、迁移、API 与定向测试；
3. 前端 Agent 基于该提交接线，不自行修改数据库约束、权限、发布事务或 profile identity；
4. 每个完整子步骤形成小而可回滚的提交，不使用 force push，不 reset 已完成历史，不删除或清空 `.env`；
5. Review 从最新 `main` 启动新的上下文；发现问题先写 findings，再在 `main` 修复并追加验证记录；
6. 一个任务完成、记录和审查收口后，才进入下一个任务。

主分支直推不等于可以多人并行改同一批文件。需要并行思考时只能使用只读审查，写入仍按后端 → 前端 → Review 顺序执行。

## 5. 自动化与浏览器验收口径

### 5.1 自动化测试

每个任务按风险选择最小充分集合：

- `pnpm lint`、`pnpm typecheck` 为常规基础；
- 改动 Nuxt 路由、运行时、迁移或生产输出时执行 `pnpm build`；
- 只运行与本次字段、API、迁移、页面路径直接相关的 unit/integration/E2E；
- 跨认证、发布、媒体、公开投影或全局 Schema 的变更可以扩大回归；
- 全量 `pnpm test`、`pnpm test:integration`、`pnpm test:e2e`、`pnpm verify:production` 主要保留给 T31–T34、跨层高风险修复和明确要求的总门禁。

自动化测试仍是回归证据，但不再用“总数很多、全部绿色”证明页面好用。

### 5.2 GPT-5.6 Sol 浏览器与视觉 Review

每次含 UI、公开投影、媒体或用户操作的任务，Review 必须实际启动应用并完成：

- 使用管理 Host 登录，按真实顺序点击创建、编辑、保存、冲突、失败、恢复和重新加载；
- 使用公开 Host 以新访客浏览对应页面，核对 SSR 后的标题、图片、事实、筛选、导航和隐藏状态；
- 至少检查 390×844、768×1024、1440×900 中与改动相关的视口；
- 观察图片是否真实解码、是否请求了错误横竖资源、是否横向溢出、焦点/键盘是否可用；
- 查看浏览器 console、network、失败响应、截图或 trace，而不是只看选择器和 HTTP 200；
- 对版本冲突、非法字段、缺图、下架阻断、匿名私有读取等负路径进行实际操作；
- 在实施记录中写清“点了什么、看到了什么、哪里失败、如何恢复”。

Review 结论至少分为 `PASS / PASS WITH FOLLOW-UP / NOT PASS`。GPT-5.6 Sol 即使参与了后端实现，也必须用新的上下文重新审查，不能用实现过程中的自测代签用户体验。
