# 跨平台迁移换行校验修复

## 原因与范围

0052 在提交前已于本地开发库执行，当时文件使用 CRLF。仓库 `.gitattributes` 要求 LF，提交并切回 main 后文件为 LF。现场重建 CRLF 文件的 SHA-256 与数据库记录完全一致，差异仅为换行字节。

用户明确要求直接在 main 修复，并要求考虑 Ubuntu 部署及其它文件。完整核对了 53 个 SQL 迁移：当前工作树均为 LF，且逐字节等于 Git 中的版本。JSON journal 通过 JSON 解析，换行不会改变其字段，不需特殊处理；图片、字体等资产哈希不在此次修改范围内。

## 最终修复

- 不添加 0052 专用哈希白名单；统一在 `migrationHashMatches` 中处理所有迁移的完整 LF / CRLF 文件形态。
- 保留原始文件哈希直接匹配的快速路径；不匹配时，从 Drizzle 无损分割的 SQL 段还原文件，计算 LF 和 CRLF 两种候选哈希。
- 只接受同一时间戳、同一份 SQL 的换行变体，不忽略 SQL token、空格、注释或文件顺序变化。
- 保留已有 0036 的明确历史 SQL 兼容项，其查找键采用 LF 文件身份，避免当前工作树换行影响旧兼容规则。
- 不修改任何历史迁移文件、不重写 `__drizzle_migrations`；迁移、readiness 和恢复校验通过同一入口获得修复。
- 不新增仓库测试或断言；现有数据库、readiness、历史兼容测试 32 项通过。本地 `pnpm db:migrate` 返回 `applied: 0`。

## Ubuntu / Linux 实证

在 WSL Ubuntu-2204、Linux/x64、Node v24.18.0、项目锁定的 Drizzle 与 better-sqlite3 上，使用隔离临时数据库执行真实迁移和备份/恢复；未访问生产数据库，也未修改仓库 SQL。

| 输入 | 换行切换后的检查 | 新建迁移数 | 重复执行数 | 历史记录 | 完整性 / 外键 | 恢复 |
| --- | --- | --- | --- | --- | --- | --- |
| 全部 LF | 使用 CRLF 文件校验 | 53 | 0 | 原样保留 | ok / 0 | 通过 |
| 全部 CRLF | 使用 LF 文件校验 | 53 | 0 | 原样保留 | ok / 0 | 通过 |

随后在临时迁移文件追加一条注释（不属于换行转换），迁移与恢复均拒绝，证明仍执行内容完整性校验。

证据：[linux-migration-eol.json](../evidence/linux-migration-eol.json)。这证明跨平台迁移行为，不代签目标生产库的迁移状态。历史文件若曾使用无法重建的混合换行或真实 SQL 改写，仍需有证据的单独核对，不接受任意历史哈希。
