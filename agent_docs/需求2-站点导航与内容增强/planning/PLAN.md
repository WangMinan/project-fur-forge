## 4. 技术决策

- **导航继续复用单一事实源**：T17-F3 取消委托二级菜单，但不删除通用 children 能力；“关于我们”仍使用它，桌面、移动和页脚继续共用 `PUBLIC_NAV_ITEMS`。
- **联系方式用固定平台枚举 + 数据数组**：业务值可配置，展示模板只循环一次；五个平台不需要关系表。
- **二维码复用媒体链**：私有源图和公开派生边界是现有安全基线，不能把后台上传 URL直接放到公开页。
- **二维码低分辨率适配复用 FFmpeg 私有源**：和作品管理一样，原图只保存一次，适配源以不可变身份写入私有 `preprocess` 变体；公开 `contact-qr-v1` 只消费适配后的 READY 来源。
- **搜索用 GET + 服务端过滤**：保持 SSR、普通链接分页和无 JavaScript 可用；当前数据量不需要 FTS。
- **FAQ 用迁移追加**：用户已明确首版只需固定模板；继续复用 FAQ，避免新增表单。
- **动态首版纯文本列表**：满足参展、掉落、开单和公告；图片、富文本、详情页等到真实需求出现再加。
- **不新增依赖**：原生 Vue/Nuxt、Zod、SQLite 和现有上传链足够。

## 5. 动态后台方案决策记录

| 维度 | A：`/admin/site/content` + JSON | B：独立 `/admin/updates` + 表 |
| --- | --- | --- |
| 首次实现量 | 较小；复用文案 Card 和分区 PUT | 较大；增加迁移、CRUD API 和管理页 |
| 数据模型 | singleton 中一个有界 JSON 数组 | 每条动态一行，模型清楚 |
| 并发 | 改一条也保存整个数组，冲突影响全部动态 | 每条独立版本，冲突范围小 |
| 发布/下架 | 能做，但逻辑嵌在数组更新中 | 天然适合逐条状态与发布时间 |
| 数量增长 | 适合约 20 条以内、低频维护 | 适合持续发布、分页与历史保留 |
| 后续扩展 | 图片、置顶、详情页会越来越别扭 | 后续加字段或媒体关联更自然 |
| 后台心智 | 所有固定文案在一页，但 Card 会继续变长 | 多一个清楚的“动态管理”入口 |
| 风险 | JSON 损坏或整组覆盖的影响更大 | 文件和测试更多，但边界更明确 |

**结论：选择 B。** 用户于 2026-08-12 确认独立 `/admin/updates` + `updates` 表。原因是“最新动态”会持续新增并逐条发布/下架；方案 A 取消且不实施。
